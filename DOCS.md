# GameServerStatus — Technical Reference

Architecture, internals, and extension points. For installation and end-user configuration, see [SETUP.md](SETUP.md).

---

## 1. Architecture

A single `StatusController` instance owns:

- A polling interval (`config.UpdateInterval` seconds, minimum 15).
- A per-server pipeline executed every tick: **query → embed build → message upsert → optional voice rename**.
- An in-memory `cache` (Map<serverKey, queryState>) populated each tick and consumed by button handlers.
- A persistent `state.json` keyed per server, holding the published `messageId` and (optionally) voice-channel metadata.

The addon is fully event-driven: there are no slash commands and no message commands. The only user-facing surface is the auto-updating embed plus its three buttons.

## 2. Entry point & addon loader integration

[gameServerStatus.js](gameServerStatus.js) exports the addon descriptor:

```js
module.exports = {
    name: 'GameServerStatus',
    version: '1.1.0',
    description: t('addon.description'),
    author: 'Naghell & contributors',
    run(client, _eventManager) { ... },
    unload() { ... }
};
```

- `run(client)` first calls `verifyGamedig()` to confirm the `gamedig` package is installed in the host bot's `node_modules/` (see §14). Then it loads config, builds a `StatusController`, and binds an `interactionCreate` listener on the Discord client. A guard flag (`client.__gssInteractionBound`) prevents double-binding across reloads. `dispatchButton()` filters on `customId.startsWith('gss_')`.
- Note: only the direct `client.on('interactionCreate', ...)` listener is registered. An earlier version also exposed an `events: { 'discord:interactionCreate': ... }` hook for Drako's `EventManager`, but having both paths caused each click to be dispatched twice and produced `Unknown interaction` errors when the second reply hit an already-consumed token.
- `unload()` stops the controller and removes the listener inside a `try/finally`, so the listener is detached even if `controller.stop()` throws.

### How Drako's AddonLoader sees this folder

The loader scans `addons/*/` and auto-imports root `.js` files only. It **excludes**:

- `utils/` and `data/` directories
- any `*config.yml` or `*.json` file

That's why `config.yml` lives at the addon root (it's user-editable data, not code) and all helpers live under `utils/`. `data/state.json` is created at runtime and never touched by the loader.

## 4. Message lifecycle

Per tick, for each configured server:

1. `StatusController.tick()` iterates `config.Servers`.
2. `processServer(server)` calls `queryServer(server)` → wraps `gamedig.query()`. On failure, returns `{ data: offlinePayload(), error }` (offline payload still produces a valid embed).
3. The result is stored in `controller.cache.set(serverKey, { data, serverConfig, serverAddress, gameType })`. Button handlers consume this cache.
4. `embedBuilder.buildEmbed(server, data, serverKey)` returns `{ embed, components }`. Components are gated on `EmbedSettings.<Button>.Enabled`.
5. `upsertMessage()`:
   - Loads existing `messageId` from `state.json`.
   - If present, calls `channel.messages.edit(...)`.
   - If the edit throws with `code === UNKNOWN_MESSAGE_CODE (10008)` or the message is otherwise unreachable, falls back to `channel.send(...)`, then `stateStore.set(serverKey, { messageId, channelId, updatedAt })`.
6. If `VoiceDisplay.Enabled`, `voiceDisplay.update(...)` renames each enabled channel using templates from `lang/<code>.yml`.

### Orphan cleanup

Runs once at `start()` if `CleanupOnStartup: true`:

1. `channel.messages.fetch({ limit: CleanupScanLimit })` — capped at Discord's hard limit of 100.
2. Filters via `isOurMessage(m)` (zero-width footer signature, see §10) and `isLegacyServerCheckMessage(m)` (button customId starting with `servercheck_`, from the previous prototype).
3. Adopts the most recent matching message for the current server (extracts `serverKey` from the button `customId`) — preserves the existing message instead of resending.
4. The rest go through `channel.bulkDelete()`. Messages older than 14 days (Discord limitation) fall back to per-message `delete()`.

## 5. State persistence

**File:** `addons/GameServerStatus/data/state.json` (auto-created on first upsert).

**Server-key derivation:** `sanitizeServerKey(ServerIP)` in [serverQuery.js](utils/serverQuery.js) — non-alphanumeric → `_`, lowercased. Example: `mc.comunidadreborn.net:25565` → `mc_comunidadreborn_net_25565`.

**Schema:**

```json
{
  "mc_comunidadreborn_net_25565": {
    "messageId": "1234567890123456789",
    "channelId": "1342285873617571892",
    "updatedAt": 1715812345678,
    "voice": {
      "categoryId": "...",
      "channels": {
        "Status":      { "id": "...", "lastName": "🟢 Status: Online",       "lastUpdate": 1715812345 },
        "PlayerCount": { "id": "...", "lastName": "👥 Online: 50/100",       "lastUpdate": 1715812345 },
        "IP":          { "id": "...", "lastName": "📡 IP: mc.example.net",   "lastUpdate": 1715812345 }
      }
    }
  },
  "gmod_45_235_98_222_27750": { "messageId": "...", "channelId": "...", "updatedAt": 0 }
}
```

**Atomic writes:** [stateStore.js](utils/stateStore.js) writes to `state.json.tmp` then `rename`s. Multiple concurrent calls chain on a single in-memory promise (`writeChain`) so writes never interleave. Rewrites only happen when the in-memory state actually changes (no-op no-write).

**Corruption recovery:** if the file fails to parse on boot, the addon logs `state.corrupted` and starts from an empty state (the lang key is in [lang/en.yml:52](lang/en.yml#L52)). Next upsert recreates a clean file.

## 6. Button interaction protocol

**`customId` format:** `gss_<type>_<serverKey>` where `<type> ∈ { connect, players, copyip }`.

**Construction:** `buildButtonId(type, serverKey)` in [embedBuilder.js:64](utils/embedBuilder.js#L64).

**Dispatch flow** ([interactionHandler.js](utils/interactionHandler.js)):

1. `interaction.customId.split('_')` → `['gss', type, ...keyParts]`. The key is `keyParts.join('_')` (server keys may contain underscores from sanitization).
2. `controller.getCachedState(serverKey)` — if missing, reply with `interactions.noFreshData` and exit.
3. Branch on `type`:
   - `connect` → `formatConnectResponse()`. Game-aware: `gameType === 'garrysmod'` adds `steam://connect/...`; `gameType === 'minecraft'` adds a manual-connect hint.
   - `players` → `formatPlayersResponse()`. Splits humans/bots from `data.players.list` and `data.players.bots`. Truncates at 1900 chars (Discord's 2000-char message limit minus a buffer).
   - `copyip` → `formatCopyIpResponse()`. Just a code-block with the address.
4. All replies use `MessageFlags.Ephemeral` so they're only visible to the clicker.

**Button visibility gating** (in `buildEmbed()`):

- `ConnectButton`: always rendered if `Enabled !== false`. Disabled (greyed out) when `!isOnline`.
- `CopyIPButton`: always rendered if `Enabled !== false`.
- `PlayersButton`: rendered only when `Enabled !== false` **AND** `isOnline` **AND** `data.players.list.length > MaxPlayersInList`.

## 7. Voice display internals

[voiceDisplay.js](utils/voiceDisplay.js) handles the optional voice-channel display.

**Category resolution order:**

1. `VoiceDisplay.CategoryID` if set → fetch by ID.
2. Else, if `VoiceDisplay.CategoryName` is **empty** → no category. Voice channels are created at the guild root (no `parent`). This is the default.
3. Else, search the guild for a category whose name matches `VoiceDisplay.CategoryName`. Adopt if found.
4. Else, create a new category with that name.

When there's no category, `state.voice.categoryId` is stored as `null` and the per-channel logs use the `voice.logs.noCategoryLabel` placeholder (e.g. `(no category)`).

**Channel permissions:** each channel is created with `Connect` and `Speak` denied for `@everyone`. Display only — not a chat room.

**Rate-limit guards** (Discord caps renames at 2 per 10 min per channel):

- If the computed new name `===` current name → skip (no API call).
- Else, enforce `MinUpdateInterval` per channel based on `lastUpdate` in `state.json`. Throttled renames log `voice.logs.rateLimited` when `Debug: true`.

**Persistence:** the category ID and per-channel `{id, lastName, lastUpdate}` are stored under the server entry's `voice` subtree in `state.json`. Restarts re-adopt by ID without recreating.

**No auto-delete:** the addon never deletes voice channels — not on `unload`, not when `Enabled: false`, not when a server is removed from `Servers[]`. Channels persist across restarts to avoid flicker.

**Permission failures:** if `Manage Channels` is missing, the setup logs `voice.logs.permissionMissing` and silently skips voice for that server. The embed keeps working.

## 8. i18n system

[utils/i18n.js](utils/i18n.js) loads `lang/<config.Language>.yml` on boot and exposes `t(key, vars)` for placeholder interpolation (`{name}` style).

**Fallback chain:**

- Active language not found → fall back to `en` (logs `config.invalidLanguage`).
- File parse error → fall back to `en` (logs `config.langFileError`).
- Missing key inside the active file → returns the raw key string (and logs `config.missingKey`).

**String namespaces** (see [lang/en.yml](lang/en.yml) for the full reference):

| Namespace | Purpose |
|---|---|
| `addon.*` | Addon metadata (description used in `module.exports`). |
| `lifecycle.*` | Boot/shutdown logs, tick errors. |
| `interactions.*` | Button reply text + game-specific hints. |
| `messages.*` | Edit/send/scan/cleanup log lines. |
| `state.*` | `state.json` corruption + save errors. |
| `migration.*` | Schema migration logs. |
| `config.*` | Config validation errors and warnings. |
| `embed.footer.<gameType>` | Per-game footer text (`minecraft`, `garrysmod`, `default`). |
| `embed.fields.*` | Embed field titles. |
| `embed.buttons.*` | Button labels. |
| `voice.*` | Voice-channel name templates + voice logs. |

**Voice template placeholders:** `{online}`, `{max}`, `{ip}`, `{version}`, `{map}`, `{gameMode}`, `{server}`.

**Adding a language:** copy `lang/en.yml` to `lang/<code>.yml`, translate values, keep `{placeholders}` intact, set `Language: "<code>"` in config, restart.

## 9. Footer resolution per game

`resolveFooterText(gameType)` in [embedBuilder.js:22](utils/embedBuilder.js#L22):

1. Looks up `embed.footer.<gameType>` in the active lang file.
2. If found → returns it.
3. If the key is unresolved (i18n returns the literal key) → falls back to `embed.footer.default` with `{game: gameType}` substituted.

To customize the footer for a new game, add a key under `embed.footer.<gameType>` in every `lang/*.yml`. No code changes needed.

The old `FooterText` config field (from the prototype) is gone. Migrations from `1.0.0` leave it in user files harmlessly — it's just ignored.

## 10. Footer signature trick

Every embed footer gets a constant suffix of 8 zero-width characters appended via `buildFooterText()` in [embedBuilder.js:17](utils/embedBuilder.js#L17):

```
GSS_SIGNATURE = ZWSP + ZWNJ + ZWJ + WORD_JOINER + ZWNJ + ZWSP + ZWJ + ZWNJ
```

Invisible to users in Discord. Used by `isOurMessage(message)` during startup cleanup to recognize the addon's own messages **without storing per-message metadata**. The server identity is encoded in each button's `customId` (also invisible to users). `getServerKeyFromMessage()` reads it back by walking the message's components.

**Legacy marker:** the previous prototype used a visible `[GSS:<key>]` footer marker. `LEGACY_VISIBLE_MARKER` (`[GSS:`) is still recognized by `isOurMessage()` so cleanup sweeps old messages too.

`isLegacyServerCheckMessage()` recognizes messages from an even older `ServerCheck` addon (buttons with customId starting with `servercheck_`) and includes them in the cleanup pass.

## 11. Config migrations

The top-level `Version` key in `config.yml` tracks the schema version. [configMigrator.js](utils/configMigrator.js).

**Boot-time comparison:**

| Config version vs `LATEST_VERSION` | Behavior |
|---|---|
| Equal | No-op. |
| Older | Apply the `MIGRATIONS` chain in order; overwrite `config.yml`; preserve the original as `config.yml.bak.v<old>.<timestamp>`. |
| Newer | Log `migration.aheadOfCode` and skip. Means the config came from a future addon version — check whether the addon itself needs updating. |

**Migration contract:** each step **only adds missing fields** with safe defaults. Existing values are never overwritten — every insert is guarded with `if (!server.X)` so migrations are idempotent and safe to re-run.

> ⚠️ **Comments in `config.yml` are lost on migration.** The migrator uses `js-yaml`'s `dump()` to round-trip the object, which doesn't preserve comments. The `.bak` file retains them. If you keep heavily commented configs, copy comments back from the backup after a migration.

### Known migrations

None — the config schema is still at `1.0.0`. The `MIGRATIONS` array in [configMigrator.js](utils/configMigrator.js) is empty. Once the schema starts evolving, append entries here following the contract below.

### Adding a new migration

In [configMigrator.js](utils/configMigrator.js):

1. Bump `LATEST_VERSION`.
2. Append an entry to `MIGRATIONS`: `{ from: '1.1.0', to: '1.2.0', apply(config) { ... } }`.
3. Keep the `apply()` body idempotent (guard with `if (!server.X)` before inserting).
4. Bump `Version` in the `DEFAULT_CONFIG_YAML` string in [configLoader.js](utils/configLoader.js) **and** the addon's `version` in [gameServerStatus.js](gameServerStatus.js) to match.

## 12. Known engineering limits

- **Startup cleanup scans ≤ `CleanupScanLimit`.** Discord's `messages.fetch` caps at 100 per call. The addon doesn't paginate. If you have hundreds of stale messages, raise the cap or delete them by hand.
- **`bulkDelete` can't delete messages older than 14 days.** Cleanup falls back to per-message `delete()`, which respects rate limits but is slower.
- **Auto thumbnail is Minecraft Java only** (via `api.mcstatus.io/v2/icon/<host>`). For other games, set `EmbedSettings.ThumbnailImage` to a URL.
- **Voice channel renames are hard-capped at 2 per 10 min per channel** by Discord, regardless of `MinUpdateInterval`. Lowering `MinUpdateInterval` doesn't let you rename faster — it just causes throttled renames to be skipped.
- **No paginated player list.** If a server reports a player list longer than ~1900 characters, the "View all players" reply is truncated with `...` (Discord's 2000-char limit per message).

## 13. Extension points

### Adding a new button

1. In [embedBuilder.js](utils/embedBuilder.js): inside `buildEmbed()`, build a new `ButtonBuilder` with `setCustomId(buildButtonId('<newtype>', serverKey))`. Gate visibility on `settings.<Name>Button.Enabled !== false`.
2. In [interactionHandler.js](utils/interactionHandler.js): add a branch in `handleButton()` for `type === '<newtype>'` returning the formatted response.
3. In [configLoader.js](utils/configLoader.js): add `<Name>Button: { Enabled: true, Emoji: '...' }` to `DEFAULT_CONFIG_YAML` and guard with `server.EmbedSettings.<Name>Button = server.EmbedSettings.<Name>Button || {}` inside `validate()`.
4. In every `lang/*.yml`: add `embed.buttons.<newtype>` and `interactions.<response-key>`.
5. Bump the addon version + add a migration that inserts the new field on old configs.

### Adding a new voice channel type

1. In [voiceDisplay.js](utils/voiceDisplay.js): append the type to `CHANNEL_TYPES` at the position it should appear in the category (creation order = display order in Discord). Add it to `TYPE_TO_LANG_KEY`. If the channel name doesn't depend on online/offline state, also add it to `STATIC_FORMAT_TYPES`.
2. In [configLoader.js](utils/configLoader.js): append the type to the list inside `validate()` so the validator initializes it.
3. In every `lang/*.yml`: add the template under `voice.<newtype>` (`online` + `offline` for status-dependent types, or `format` for static ones).
4. Add the type to `DEFAULT_CONFIG_YAML.VoiceDisplay.Channels` in [configLoader.js](utils/configLoader.js) and to the migration step in [configMigrator.js](utils/configMigrator.js) so existing configs get it.

### Adding a new supported game

Usually nothing to do — `gamedig` handles the protocol. To customize the footer text for the new game, add a key under `embed.footer.<gameType>` in every `lang/*.yml`. `resolveFooterText()` falls back to `embed.footer.default` automatically otherwise.

If the game needs a custom thumbnail, the user can set `EmbedSettings.ThumbnailImage`. To wire in an auto-thumbnail source (like `mcstatus.io` for Minecraft), extend the thumbnail block in `buildEmbed()` at [embedBuilder.js:134](utils/embedBuilder.js#L134).

## 14. Host-managed dependency

The addon's only dependency, [`gamedig`](https://github.com/gamedig/node-gamedig), is **not bundled** inside the addon folder. The customer adds `"gamedig": "^5.3.2"` to their bot's root `package.json` and runs `npm install` once.

**Why host-managed and not bundled:**

Two earlier approaches were tried and discarded:

1. **Auto-install at runtime** via `child_process.spawn('npm install ...')`. Fails on Pterodactyl eggs (`npm` not on PATH at runtime), read-only Docker containers, and restricted-user hosts. Discarded.
2. **Bundled `node_modules/` inside `utils/`** (kept the AddonLoader from scanning it). Worked locally but added ~5 MB to every distribution, and `require.resolve('./utils/node_modules/gamedig')` from `gameServerStatus.js` produced false negatives on some Node setups because gamedig 5.x uses the shortcut form of conditional exports (`{"import": ..., "require": ...}` instead of `{".": {"import": ..., "require": ...}}`) and Node's relative-path resolver doesn't apply the exports field consistently in that case. Discarded.

The current approach trades a one-time manual install for fewer moving parts: standard npm dependency, no AddonLoader edge cases, no Node-version-specific quirks. The cost is exactly one extra step in [SETUP.md §1](../SETUP.md).

**Resolution path:**

[gameServerStatus.js](gameServerStatus.js) calls `require.resolve('gamedig')` (bare specifier) on boot. Node walks `node_modules/` directories upward from the addon's location until it finds `<bot-root>/node_modules/gamedig`. Bare-specifier resolution applies the exports field correctly for both directory existence and entry-point selection, so the false-negative seen with relative-path resolution does not happen here.

[serverQuery.js](utils/serverQuery.js) wraps `require('gamedig')` in `getGameDig()` so the actual require runs lazily — after `verifyGamedig()` has already confirmed the package is installed. Without the lazy wrap, a missing dependency would throw `Cannot find module 'gamedig'` at module-load time, before any helpful log could be printed.

**Updating gamedig:** the customer pulls a new addon version + a corresponding line in [SETUP.md §1](../SETUP.md) bumping the version specifier, e.g. `"gamedig": "^5.4.0"`. No vendor folder to repackage.
